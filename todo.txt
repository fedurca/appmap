SUPPLY CHAIN — HOTOVO
=====================

Piny jsou doplněné skutečnými hodnotami a enforce=true, takže každá
regrese teď shodí CI.

  SEC-040  všech 15 Actions zapíchnuto na commit SHA
  SEC-044  base image na digest multi-arch indexu
           sha256:2c941e86...63c4a (python:3.12-slim, upstream 2026-08-16)
  SEC-033  Sigstore ověření podpisu python.org před rozbalením

Poznámky k tomu, jak se to dělalo:

  - Resolver jsem přepsal z REST API na `git ls-remote`. API vrátilo pro
    actions/checkout@v4 JINÝ commit než na co ten tag ukazuje, a hlavně
    neumí peelovat anotované tagy — u 4 z 15 Actions (attest-build-provenance,
    snapcore/action-build, flatpak, cosign-installer) je `refs/tags/vX`
    SHA tag OBJEKTU, ne commitu. Takový pin GitHub nespustí.
  - Každý SHA je navíc ověřený `git fetch --depth 1 <sha>` proti tomu
    repu — pin, který nikdo nezkontroloval, je pin, který může být překlep.
    To dělá i `--write` automaticky a odmítne zapsat neověřitelnou hodnotu.
  - SEC-033: python.org publikuje vedle souboru jen MD5. Chosen-prefix
    kolize na MD5 jsou praktické, takže jako supply-chain kontrola je to
    k ničemu. Místo hashe se ověřuje Sigstore bundle, který python.org
    taky publikuje — silnější tvrzení a nepotřebuje novou hodnotu pro
    každý patch release. Identity release managerů jsou v
    packaging/windows/python-embed-trust.json, opsané z
    https://www.python.org/download/sigstore/ (pozor, issuer NENÍ u všech
    Google — 3.14+ používá GitHub OAuth).

Obnova pinů:  python packaging/pin_supply_chain.py --write
Dependabot je pak drží aktuální sám.


OVĚŘENÍ — CO UŽ JE HOTOVÉ
=========================

Ukázalo se, že většina "potřebuje reálný stroj" reálný stroj nepotřebuje.
Všechno níže běží v CI (joby "hardening" a "container-uid"), takže se to
neověřuje jednou, ale při každém commitu.

[x] visudo -cf na obou generovaných sudoers, i s uživatelem s tečkou
[x] systemd-analyze security --offline=true na všech unitách i na
    base+drop-in (systemd 255 běžící systemd nepotřebuje)
[x] ProtectSystem=strict vs. StateDirectory — nekolidují
[x] Docker UID 65532
[x] SIGTERM na commatrix serve — end-to-end, včetně requestu v letu
[x] elevate-linux --revoke: kontrola unit User nehlásí falešný poplach
[x] elevate-linux --profile topology: degradace atribuce ZMĚŘENA

Co ta měření našla (detaily v CHANGELOG.md):

  1. Profil topology byl MÉNĚ uzavřený než attribution a horší než
     žádná elevace (6.5 vs 5.2 vs 6.4). Celý sandbox blok seděl uvnitř
     větve attribution. Opraveno; teď 4.3 vs 4.4.
  2. V kontejneru nefungoval ŽÁDNÝ read-only příkaz. Není to výstupní
     adresář, ale adresář databáze: WAL čtenář musí vedle DB vytvořit
     -shm. Opraveno fallbackem na immutable režim.
  3. CODE-006 byla opravená jen z půlky. Obsloužit SIGTERM nestačí —
     ThreadingHTTPServer používá daemon vlákna, takže request v letu se
     zabil. Naměřeno: SIGTERM během /ingest merge = prázdná odpověď
     klientovi a NULA uložených řádků. Doplněn grace period.
  4. Degradace u --profile topology je drastická, ne mírná: 92 % → 8 %
     pokrytí atribuce, a 0 % u socketů cizích uživatelů. Číslo je teď
     v nápovědě `--profile` i ve varování při elevaci. Změř si to na
     svém hostu: packaging/measure_attribution.py

POZNÁMKY K NÁLEZŮM, KTERÉ NEŠLY OPRAVIT PODLE ZPRÁVY
=====================================================

SEC-028 — obvyklý postup (handler na expat přes XMLParser.parser)
  v Pythonu 3.9+ nefunguje: xml.etree ten atribut přestal vystavovat.
  Kód napsaný tímhle způsobem tiše nedělá nic a vlastní test projde.
  Ověřeno; nahrazeno odmítnutím DOCTYPE/ENTITY/NOTATION před parsováním
  (v XML je '<' v datech vždy escapované, takže shoda je přesná).

SEC-028 v praxi — samotný wrapper "<Events>" + text + "</Events>"
  už DOCTYPE blokuje (syntaktická chyba). Hardening je tedy obrana do
  hloubky, ne oprava aktivně zneužitelné díry. Test to reflektuje:
  kontroluje _reject_dtd() přímo, ne přes wrapper.

SEC-023 — heslo se z argv odstranilo úplně, ne jen zamaskovalo:
  účet se zakládá PowerShellem přes stdin, úloha se registruje z XML
  s LogonType=S4U, které heslo nepotřebuje. Staré cesty zůstaly jako
  fallback a samy hlásí, že secret vystavují.

SEC-034 — zpráva mluví o "deploy implicitně jako root". Skutečný
  problém je, že root byl VÝCHOZÍ, čímž se na každém spravovaném
  hostu zahodil celý least-privilege model nástroje. Výchozí je teď
  servisní účet + capability set; root je explicitní opt-in.

CODE-030 — bytes_sent/bytes_recv z iphlp jsou dnes vždy 0 (ESTATS
  není implementované), takže have_bytes byl v praxi vždy False.
  Oprava je přesto správná: přidán explicitní příznak 'accounted',
  aby se 0 nedala zaměnit s "neptali jsme se". Až se ESTATS doplní,
  per-edge logika už bude na místě.
